# Praise app audit — 12 October 2026

Reviewed commit: `b1251cc`. Release declared in `pubspec.yaml`: `1.0.0-beta.3+4`.

## Assessment

Praise is a substantial Android-first beta with most core offline workflows implemented. Its local-first architecture is appropriate for finding and reading worship songs in unreliable network conditions. It is ready for focused beta hardening, but I would not call it ready for a broad production release until catalogue consistency, list deletion/reordering, role navigation, and support submission integrity are fixed.

No P0 defect was established. Several P1 defects affect content correctness or advertised workflows. Passing existing tests does not establish release readiness: additional audit probes reproduced defects outside the current coverage.

This report covers Flutter source, data repositories, SQLite migrations, navigation, reader and export implementations, Android native OCR/AI/audio, iOS configuration, catalogue tools and data, the browser editor, support services, CI, and release workflows. UI observations come from source inspection and widget checks. No Android device was connected; Android builds, native execution, Play delivery, actual share sheets, TalkBack, and visual usability on a physical device were not verified. iOS could not be built here because full Xcode and CocoaPods are unavailable. Deployment credentials, production infrastructure settings, editorial permissions, and store submission status were not inspected.

## Critical issues and release blockers

### P1 — Catalogue upgrades can overwrite newer remote data without correcting its version

Evidence: [seed_service.dart](/Users/samireddynani/projects/praise/lib/core/database/seed_service.dart:15), [catalogue_sync_service.dart](/Users/samireddynani/projects/praise/lib/features/catalogue_sync/data/catalogue_sync_service.dart:88).

`SeedService` uses a hard-coded seed marker `11`, while the checked-in catalogue manifest is version 13. When the seed marker differs, it upserts all bundled server rows without checking the installed remote version. It leaves `remote_catalogue_version` unchanged. An app update can therefore replace newer downloaded lyrics with older bundled lyrics while refresh still reports that the catalogue is current. Changed bundled assets also do not reload for installations already marked seed 11 unless somebody manually increments that constant.

An in-memory audit probe reproduced replacement of newer content while retaining remote version 13. Coordinate seed and remote provenance using a generated bundle version/hash, prevent downgrade, and reconcile deleted server rows and metadata atomically. Cover an app upgrade after a newer remote refresh, not only first installation.

### P1 — Structured arrangements and practice videos are inconsistent across refreshes

Evidence: [catalogue_models.dart](/Users/samireddynani/projects/praise/lib/features/catalogue_sync/data/catalogue_models.dart:201), [catalogue_store.dart](/Users/samireddynani/projects/praise/lib/features/catalogue_sync/data/catalogue_store.dart:90), [song_structures.json](/Users/samireddynani/projects/praise/assets/data/song_structures.json).

The remote song model has no structure field, and the publisher does not include the separate structured-arrangement asset. Existing `structureJson` survives a remote upsert even when `body` changes. The structured reader can consequently display stale lyrics and chords alongside newer catalogue text. New remote songs cannot receive arrangements through this pipeline.

The current checked-in remote snapshot also has no practice-video fields, although the bundle contains them. Snapshot application writes null video URLs over existing links. An audit probe confirmed video removal and preservation of stale structure on a text update.

Use one versioned song/arrangement contract throughout editor, validation, bundle, snapshot, delta, and persistence. Associate arrangements with a lyric revision; replace or invalidate incompatible structure during updates. Make bundle and remote metadata consistent before publishing.

### P1 — Deleted catalogue songs break list ordering and inflate displayed counts

Evidence: [collections_repository.dart](/Users/samireddynani/projects/praise/lib/features/collections/data/collections_repository.dart:49), [reorderSongs](/Users/samireddynani/projects/praise/lib/features/collections/data/collections_repository.dart:201).

Sync soft-deletes songs but preserves membership rows. List detail hides deleted songs; list summaries count all memberships; reorder validation expects all memberships. After one song disappears from a catalogue, the screen can show fewer songs than its count, and reordering the visible list is rejected.

An audit probe reproduced a count of two with one visible song and a reorder exception. Define a consistent policy: retain hidden memberships for possible restoration while reordering active members, or clean them up with an explicit product decision. Preserve user intent and add a regression covering delete, reorder, and later restoration.

### P1 — Change role is inaccessible after onboarding

Evidence: [router.dart](/Users/samireddynani/projects/praise/lib/app/router.dart:27), [settings_screen.dart](/Users/samireddynani/projects/praise/lib/features/settings/presentation/settings_screen.dart:78).

Settings navigates to `/starter?change=true`, but the router redirects every `/starter` visit to `/songs` when onboarding is complete. The change-role flag is never considered. A mounted router/widget probe confirmed the redirect.

Allow this explicit settings flow or provide a separate role-settings route. Save role and feature defaults in one transaction; currently onboarding completion is written before all feature defaults. Test first launch, completed onboarding, change role, and preservation/reset of customized switches.

### P1 — Support reports lose submitted content while returning success

Evidence: [worker.js](/Users/samireddynani/projects/praise/support_worker/src/worker.js:365).

The Worker accepts fields of up to 6,000 characters but truncates each Discord field beyond 1,024. It does not retain the full submission elsewhere. A mocked local request containing 5,000 lyric characters returned HTTP 201 while only 1,018 characters reached the outgoing payload.

Send the full text through a bounded attachment or safe multipart/message strategy, or reject oversized input with a visible limit. Ensure a successful receipt means the complete request was retained. Add long Telugu-text tests and timeout/retry duplicate protection.

### P1 before wider public exposure — Support abuse protection is disabled in checked-in deployment configuration

Evidence: [wrangler.toml](/Users/samireddynani/projects/praise/support_worker/wrangler.toml:5), [worker.js](/Users/samireddynani/projects/praise/support_worker/src/worker.js:216).

The KV binding is commented out, and `enforceRateLimit` returns immediately without it. Setting `RATE_LIMIT_PER_HOUR=3` alone does not enforce the limit. Actual production bindings were not inspected, so this is a confirmed repository configuration gap, not a claim that the live service is currently unprotected.

Even when connected, the read/increment/write counter is not atomic. Use an enforceable platform rate limit or coordinated counter and explicit deployment validation. Cloudflare documents concurrent-write overwrites and per-key write limits for KV: [Workers KV write behavior](https://developers.cloudflare.com/kv/api/write-key-value-pairs/).

## UI/UX assessment and improvements

The existing UX has a sensible foundation: four clear destinations, cached content during refresh, contextual song actions, a closed-by-default controls panel, language preferences, empty states, lazy lists, and draft recovery. The song-controls TODO is already substantially implemented and should be marked accordingly.

1. **Fix accessible onboarding first.** The centered non-scrollable `Column` overflowed in a widget probe at 320×568 with 2× text scaling. Use a scrollable layout with an accessible Continue action, and verify landscape and keyboard constraints. Role selection needs an explicit selected semantic state. Display “Worship leader,” rather than the enum name `worshipLeader`, in Settings.
2. **Keep lyrics dominant.** Musical controls should appear only when the song has relevant data. Clearly distinguish enabling a feature from having content available. Two arranged songs do not justify implying that the whole catalogue has chords or harmony.
3. **Make search stable.** Add a short debounce, retain results during updates, guard stale pages, and provide match context. Consider punctuation/Unicode normalization before adopting full-text search; current title/author search size does not justify a server search architecture.
4. **Clarify photo and AI choices.** Present Keep photo, Extract text, and optional Organize text as understandable actions. Show model download bytes/progress, Wi-Fi waiting, cancel/retry, and supported-install requirements. Let the user continue with OCR while model preparation is unavailable.
5. **Protect work during editing.** Extend draft recovery to editing existing songs or add unsaved-change confirmation. Keep a clear recovery/discard affordance, including retained photos.
6. **Preview sharing and importing.** Show the selected language/content, photo omissions, and oversized-image PDF alternative before invoking the share sheet. Import should show actual song matches, not just a count.
7. **Validate a focused performance-reading mode.** Consider keep-screen-awake, larger quick controls, stable scroll position, and next/previous list-song navigation based on worship use. These are suggested product improvements, not missing agreed V1 requirements.
8. **Run real accessibility and visual QA.** Cover TalkBack labels, focus order, touch targets, contrast, Telugu wrapping, long titles, dark mode, 200% text, landscape, tablets, long PDFs, and share-sheet anchoring. Source inspection does not establish these results.

## Architecture assessment

Keep Flutter + Riverpod + Drift + static catalogue hosting. The source ownership boundary (`server` versus `custom`), transactional sync, UUID custom IDs, stable catalogue mapping, foreign keys, and on-device processing are good choices. A larger maintained backend is not required to resolve the current problems.

The most important architectural improvement is **one authoritative, versioned content contract**. Right now there are separate representations for plain catalogue rows, bundled structures, browser-editor exports, reader parsing, and share documents. They can disagree about lyrics, arrangement metadata, language, and revision.

The browser editor illustrates the gap: `index.html` loads only `app.js`, while tests exercise `chords.js`, `format.js`, and `transliterate.js`. The running page therefore bypasses tested chord validation/grapheme-safe insertion and repeat parsing. Its exported `music`/`lyrics`/`chordLines` object also differs from the mobile reader's `originalKey`/`sections`/`segments` structure. Connect the tested helpers to the actual UI and add an editor-export → publisher → database → reader round-trip fixture.

Refactor the 2,284-line song detail screen into reader, controls, notes, video, and photo components. Centralize repeated arrangement parsing and reading limits. Separate catalogue state transitions from screen-specific refresh handlers. Avoid adopting a large abstraction framework; these targeted boundaries are sufficient.

Separate operational and product feature flags. Current role switches are local preferences, not permissions or remotely controlled release gates. Native capability checks should decide whether unsupported OCR/AI controls are shown.

## What remains pending

**Required for a reliable release:** P1 fixes; coherent content/version schema; index invalidation and pagination protection; import preview and bounded export links; deployment abuse-control validation; native Android smoke testing; Play internal-track model testing; accessibility/visual QA; backup policy; actual release-artifact verification.

**Implemented partially:** chord/capo/harmony content and publication, browser editor integration, structured chord export, accessible role changes, public support tracking, iOS support, and full exports of photo-plus-text songs.

**Operational status unknown:** deployed AppSheet app/reviewer access, workflow secrets, catalogue-host configuration, deployed Worker bindings, release signing, Play upload/model delivery, and store review. The repository contains substantial tooling, but does not prove these external steps are completed.

**Explicitly deferred product scope:** accounts, cloud synchronization, live collaboration, presentation integration, full-text lyric search, automatic background catalogue sync, audio playback, and custom chord editing. Do not count these as defects or use them to justify an arbitrary completion percentage. Import links, transliteration, and some chord features have already gone beyond the original V1 boundary.

**Documentation cleanup:** README still describes a planning/foundation stage and Gemini Nano, while native code uses Gemma. Song counts disagree in prose. PRD out-of-scope sections conflict with implemented links/transliteration/chords; support references mix GitHub and Discord. The privacy document omits the optional model-download network use. Update docs to distinguish current beta behavior, remaining release work, and future scope.

## Recommended order of work

1. **



:** fix seed/remote coordination, arrangement/video synchronization, list deletion/reordering, role routing, and full support-submission retention. Add regression tests against intended behavior.
2. **Release hardening:** enable validated abuse controls, repair index refresh and paging, finish link/import behavior, handle startup failures, and exercise signing plus APK/AAB artifact checks.
3. **Device and UX validation:** airplane-mode fresh install/upgrade, low-memory OCR, photo recovery, model download/cancel, metronome under load, video interruptions, large text, TalkBack, PDF shaping, and share sheets.
4. **Product completion:** integrate Song Studio with publication, expand reviewed musical metadata, implement portable local backup, and decide whether iOS is a supported release target.

Release acceptance should require these gates, rather than a feature-count percentage: user data survives refresh and upgrade; displayed lyrics match the applied catalogue revision; lists remain editable after catalogue deletion; every advertised flow is reachable; success receipts preserve full submissions; and core reading works on real Android hardware offline.
